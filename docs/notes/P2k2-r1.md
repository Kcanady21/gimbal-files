## What I built

- `crates/fm-core/src/fileops/trash.rs`: a `TrashRevision` object/revision token
  on `TrashIdentity`, strict `same_object`, and a separate `agrees_with` for
  restore requests. `TrashError::Unverifiable` reports exactly “Cannot verify
  this Trash item is unchanged”. The production adapter requests `etag::value`
  and keeps it only when the backend supplies a non-empty value. The scratch
  integration backend gives every replacement at one URI a new generation.
- `crates/fm-core/src/fileops/mod.rs`: `ItemKey::{Path,Trash}` is the conflict
  key. Restores key by their typed trash URI, so several versions of one
  original path never share an answer; `Step::target` remains the destination
  used for display. `Decisions`, `ExecuteError::UnansweredConflicts`, the
  empty-plan fingerprint and the executor all use the key. Ordinary copy, move,
  rename and undo keep path keys.
- `crates/fm-core/src/fileops/tests.rs`: the two named regressions plus token
  reuse/loss/change, missing display date, stale confirmation, and the shared-
  original Skip/Keep Both/apply-all/Replace/Cancel sequences.
- `crates/fm-ui/src/fileops/conflict.rs`: `ConflictQuestion` carries the typed
  key and a separate destination/name. The dialog, apply-to-all and
  close-without-answer paths pass only keys.
- `crates/fm-ui/src/trash.rs`: the browser selection is now `TrashIdentity`
  rather than a bare URI, so a refresh drops a selection whose object token or

- `crates/fm-core/tests/trash_browser.rs`: the scratch backend models a new

## Identity guarantees and limits

**Guarantees [read/observed]:**

- `TrashIdentity::same_object` requires equal URIs and two present, equal
  backend object/revision tokens. A missing token, a changed token or no token
  is never object evidence. Optional original/date metadata is deliberately not
  part of that proof.
- `execute_empty` calls `TrashBackend::revalidate_object`, not the restore
  matcher. It refuses `Missing`, `Changed` and `Unverifiable` for that item and
  continues with the rest of the confirmed snapshot.
- `TrashIdentity::agrees_with` is the restore/normal-revalidation matcher. A
  snapshot date that disappears is now a change; a missing snapshot date is not
  by itself a change; a bare URI request from the registry is accepted and then
  the plan uses the fresh listing. A missing original still refuses restore but
  keeps the item visible.
- The empty-plan fingerprint hashes the complete identities including tokens,
  so a confirmation made for an older plan is `ConfirmationMismatch`.
- The scratch backend increments a per-URI generation on every replacement,
  even when URI, original path and second-resolution date are identical. Its
  `delete` revalidates the token again immediately before unlinking.
- Undo records for trashed entries now keep the entry path's device and inode.
  An undo refuses a recorded entry whose inode changed, and empty invalidation
  drops a record whose entry inode is gone or replaced instead of matching only
  original/date metadata.
- The browser keeps a selected identity only while it still agrees with the
  fresh listing. A later object at the same URI is not silently selected.

**Limits [read/inferred]:**

- The installed GVfs `gvfsd-trash` is **1.60.0-1ubuntu0.1**. Its binary
  advertises these attributes:
  `standard::name`, `standard::name,standard::type`,
  `standard::target-uri`, `trash::orig-path`, `trash::deletion-date`,
  `trash::item-count`, `access::can-delete/execute/rename/trash/write`,
  `time::modified,time::modified-usec` and `unix::mode`. It does not advertise
  `etag::value`, `id::file`, `unix::inode` or `unix::device`. **[observed]**
- `etag::value` and `id::file` exist as GIO attribute names, and `unix::inode`
  and `unix::device` exist in the pinned crate, but an attribute name existing
  is not backend support. GVfs source is not local, so I did not infer support
  from the names. **[read]**
- Therefore the production `GioTrash` normally has `revision=None`. Empty Trash
  can still list, confirm and report, but every such item is refused with
  “Cannot verify this Trash item is unchanged”; nothing is permanently deleted.
  This is the brief's required safe behaviour, not a working-looking button.
  If a future GVfs version supplies `etag::value`, the same code uses it.
  **[read/observed/inferred]**
- `standard::target-uri` is a symlink target attribute
  (`gio-0.22.10:src/auto/constants.rs:195-197`), not an object token, so it was
  not used.
- The executor revalidates immediately before `g_file_delete`, but GIO has no
  compare-and-delete API. A backend-side race between that query and the delete
  cannot be closed from the client. The scratch backend closes it by checking
  its generation again inside `delete`; production has no such hook. **[read]**
- A restore command carries only validated trash URIs through the existing
  registry. The browser now drops stale selections on refresh and the plan
  re-lists before execution, but a replacement between the browser's last
  listing and the worker's plan is indistinguishable when the backend supplies
  no token. Restore is non-permanent and the destination conflict checks still
  refuse overwriting; production object identity for that narrow window remains
  unverifiable. **[read/inferred]**

## Conflict keys

`ItemKey::Trash(TrashUri)` identifies each restore step; `ItemKey::Path` keeps
the existing copy/move/rename/undo behaviour. `ConflictQuestion` has both
`item: ItemKey` and `destination: Option<PathBuf>`; the dialog title uses the
destination's file name, while `ConflictFlow::answer`, `Decisions`, the worker
and the executor use only the key. A restore checks its answer with
`step.decision_key()` before it chooses Keep Both/Replace, so a Replace or Skip
cannot leak to another version that shares the original path. Keep Both still
uses the existing `free_copy_name` and `claimed` set, so two copies get
`name (copy).ext` and `name (copy 2).ext`. **[observed]**

## Backend investigation correction (ChatGPT, Nov 3, 2026)

This supersedes the earlier claim that installed GVfs lacks etag/object-identity
attributes. Absence of strings in the daemon binary was not evidence of absence.
Reviewer read upstream GNOME GVfs 1.60.0 gvfsbackendtrash.c via the web:
https://raw.githubusercontent.com/GNOME/gvfs/1.60.0/daemon/gvfsbackendtrash.c
Root enumeration at lines 635-643 and item query at 783-793 forward requested
attributes to the native trashed file. Lines 583-591 expose its native target URI;
that attribute is not restricted to ordinary symlinks in this backend. Delete at
449-493 resolves a top-level trash item and delegates deletion to the backend.
No source files were downloaded into the project or reference folders.

**[observed]** The sandboxed read-only gio probe returned Operation not supported.
The approved out-of-sandbox probe listed Trash URIs and queried three samples,
printing only attribute availability (no filenames or file contents). All three
supplied id::file, id::filesystem, unix::device, unix::inode, time::changed and its
usec/nsec components, etag::value and standard::target-uri. No item was opened,
restored, moved, trashed or deleted. This is direct installed-backend evidence,
not a destructive backend integration test or proof for every mounted filesystem.

**[read/observed]** Installed GLib is 2.88.0. Its native ETag derives only from mtime
seconds/usec/nsec; native id::file derives from device/inode:
https://raw.githubusercontent.com/GNOME/glib/2.88.0/gio/glocalfileinfo.c#L114-L138
A disposable /tmp/gimbal-empty-plan-* native-file probe set equal mtimes on two
separate files. GIO returned equal ETags but different id::file and inode. Scratch
was removed. ETag alone cannot prove that a trash object has not been replaced.

**Plan direction (not implemented):** keep GIO deletion on validated trash URIs,
replace the single ETag token with a structured object/revision fingerprint, and
revalidate inside the backend's checked-delete operation immediately before deletion.
Keep immutable confirmed top-level item sets, late-entry exclusion, per-item refusals,
UI-only confirmation and existing worker/undo protections. Explicitly document that
GIO supplies no atomic expected-identity conditional delete; do not promise complete
protection against another process swapping objects in the query/delete interval,
or a frozen recursive directory tree. A custom backend/protocol would be required
for a stronger atomic guarantee. No production source edit, gate run, commit or push
for this investigation. User requested a detailed plan before implementation.

**[read] Dolphin 25.12.3 / KIO 6.24.0:**
- `dolphin/src/trash/dolphintrash.cpp:79-89`: Trash::empty creates a confirmed

  The inspected empty path does not use an ETag admission check or atomic
  snapshot identity contract. The orphan sweep is broader than Gimbal's frozen
  top-level confirmed list, so do not port that sweep.

**[read] Thunar 4.20.7:**
- `thunar/thunar-application.c:2755-2810`: confirmation, then worker unlink job
  seeded with the Trash root. Unlike Gimbal's intended UI, this version defaults
  its dialog to Yes; retain Gimbal's Cancel default instead.
- `thunar/thunar-io-jobs.c:51-78`: collect with NOFOLLOW_SYMLINKS;

- `thunar/thunar-io-scan-directory.c:79-90`: deliberately does not recurse into

  item's contents. It enumerates top-level entries from the Trash root instead.
