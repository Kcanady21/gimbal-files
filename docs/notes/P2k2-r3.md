## What I built

- `crates/fm-core/src/fileops/trash.rs`: replaced the ETag-only
  `TrashRevision` identity with `TrashFingerprint`, built from the attributes
  GVfs actually forwards from the native trashed file. The fingerprint contains
  `id::file`, `id::filesystem`, `unix::device`, `unix::inode`,
  `standard::type`, precise `time::changed`, precise `time::modified`,
  `standard::size`, optional `standard::target-uri` and optional `etag::value`.
  Original path and deletion date remain separate display/restore metadata.
  Added `TrashBackend::query_item` and `delete_checked`, and removed the
  unconditional `delete` method. The production `GioTrash::delete_checked`
  queries the exact trash URI and then calls `gio::File::delete` on it.
- `crates/fm-core/src/fileops/mod.rs`: Empty Trash now calls only
  `delete_checked`; a missing item becomes `Skipped`, an identity/fingerprint
  change or missing identity becomes `Refused`, and backend failure remains
  `Failed`. Only successful deletions invalidate undo state.
- `crates/fm-core/src/fileops/tests.rs`: synthetic `gio::FileInfo` fingerprints
  for every supported combination, plus the new identity/change/missing-item
  regressions.
- `crates/fm-core/tests/trash_browser.rs`: the injected scratch backend now
  returns structured fingerprints and records checked-delete calls. A new
  child covers an already-gone item and a replaced item in one confirmed plan.
- `crates/fm-ui/src/trash.rs`: the Trash page keeps a visible **Details**
  button when a job has per-item failures/refusals/skips, opening an
  `adw::AlertDialog` through the existing details dialog. Details use item
  names, not internal `trash:///` URIs. The existing confirmation scoping and
  stale-reply guard are retained.
- `crates/fm-ui/src/fileops/progress.rs`: Empty Trash summaries distinguish
  deleted, failed, refused/changed, already-gone and cancelled counts. A mixed
  result never says “Trash emptied”. Skipped Empty items get a visible
  “already gone from the Trash” detail line.
- `docs/notes/P2k2-r3.md`: this file.

## Fingerprint design and supported combinations

GVfs 1.60.0 forwards the requested attributes to the real trashed file during
root enumeration and per-item query (`daemon/gvfsbackendtrash.c:635-643` and
`:783-793`). It also exposes the native file through `standard::target-uri` at
`:583-591`; that is not an original deletion destination and is never used to
build a local delete path. Delete resolves a top-level trash item and delegates
to the backend at `:449-493`. **[read]**

`LIST_ATTRIBUTES` (`trash.rs:787`) requests:

```
standard::name, standard::display-name, standard::type, standard::size,
standard::icon, standard::target-uri, trash::orig-path, trash::deletion-date,
id::file, id::filesystem, unix::device, unix::inode,
time::changed, time::changed-usec, time::changed-nsec,
time::modified, time::modified-usec, time::modified-nsec,
etag::value
```

The identity rule in `TrashFingerprint::compare_object` (`trash.rs:387-458`) is
explicit:

1. A **file/filesystem pair** is established only when both sides supply
   `id::file` and `id::filesystem`, and both values agree.
2. Otherwise a **device/inode pair** is established only when both sides supply
   `unix::device` and `unix::inode`, and both values agree.
3. Any identity component present on both sides that differs is `Changed`
   before sameness is considered. A present `standard::type` or
   `standard::target-uri` must also agree.
4. No complete pair present on **both** sides is `Unverifiable`, not “changed” and not “same”.
5. An ETag is never an ID. If both sides carry one, a different value is extra
   observed revision change; a missing ETag is not a refusal.
6. Precise `time::changed` is compared first when both sides supply it. If ctime
   is absent on one side, `time::modified` plus `standard::size` are compared
   when available. Missing optional change fields are not themselves refusals.

This deliberately fixes the native ETag weakness. GLib 2.88.0 builds the native
ETag only from mtime seconds/usec/nsec (`gio/glocalfileinfo.c:122-130`) while
`id::file` is `l<device>:<inode>` and `id::filesystem` is `l<device>`
(`:136-154`). A native ETag can therefore be equal for different files;
`id::file`, `id::filesystem` and inode can still differ. **[read]**

Attribute presence is checked with `GFileInfo::has_attribute` and the value is
read only through the attribute's actual type (`trash.rs:471-514`). This matters
because GLib writes `unix::device` as uint32 but `unix::inode` as uint64
(`gio/glocalfileinfo.c:993-997`), and `time::changed`/`usec`/`nsec` as
uint64/uint32/uint32 (`:1036-1038`). `attribute_status` reports `UNSET` for
values populated directly with `g_file_info_set_attribute_*`, so presence uses
`has_attribute`, not a status test. An absent attribute is `None`, never zero,
an empty string or a guessed value. **[observed/read]**

`gio-0.22.10` exposes the nanosecond names only behind its disabled `v2_74`
feature (`src/auto/constants.rs:288-289`, `:309-311`). I did not add a feature
or change a manifest; the exact C attribute names are string literals in
`trash.rs:784-785`. All other names use the pinned typed constants
(`constants.rs:53`, `:80`, `:83`, `:184`, `:196`, `:283`, `:331`, `:337`).
`FileInfo::has_attribute`/`attribute_string`/`attribute_uint32`/
`attribute_uint64`/`file_type` are pinned at
`gio-0.22.10:src/auto/file_info.rs:295`, `:144`, `:166`, `:174`, `:224`.
**[read]**

Original path and deletion date are not in `same_object`; they stay in
`TrashIdentity` for display and restore, and `agrees_with` keeps their existing
restore-request checks. `NOFOLLOW_SYMLINKS` is used for both enumeration and
per-item queries. Trash URIs and non-UTF-8 names are unchanged. **[read]**

## Confirmed snapshot and checked deletion

`plan_empty` still runs on the worker and builds one immutable `Vec` of
validated trash identities from `trash:///`. The UI confirmation is bound to
that exact plan by `EmptyConfirmation`'s full-identity fingerprint. Adding an
entry after the plan does not add a step. The executor never runs a second
broad empty/orphan sweep. A folder is one confirmed top-level item; its
descendants are not enumerated or frozen by the app. **[read/observed]**

`TrashBackend::delete_checked` is the only permanent-delete boundary
(`trash.rs:705-752`). The production implementation at `trash.rs:890-909`
calls `revalidate_object`, which queries the exact validated trash URI through
`query_item`, then immediately calls `gio::File::delete` on that same URI. The
previous public `delete` trait method is gone, so the executor cannot
accidentally call an unchecked production delete. The scratch backends use the
same checked operation, and their tests also record each top-level delete call.
**[read/observed]**

Deletion is still GVfs's job. The app does not delete the Trash root, walk into
trashed folders, follow symlinks, invoke `rm`, start another file manager, or
rewrite Trash storage. A failed backend stays visible; there is no fallback to
`~/.local/share/Trash`. An unavailable or unplugged backend is a per-item
`Failed`/refusal, never permission to mount or scan elsewhere. I did not port
KIO's orphan cleanup scan or add a Qt/KIO dependency, and the app performs no
second empty sweep. **[read]**

**Residual race, accepted by Kyle:** the revalidation query and the GIO delete
are two requests. Another process can still replace or change the object in
that interval; GIO has no expected-identity conditional delete. A concurrent
accidental change can cause the same race. The app does not use an advisory
lock (other file managers ignore it) and does not claim atomicity, a recursively
frozen folder tree or complete elimination of the race. The confirmed top-level
set plus immediate best-effort identity/change checks are the guarantee.
**[read/inferred]**

Cancel stops before the next item. A backend directory deletion already in
progress is not promised to interrupt immediately, and completed deletion is
permanent. No undo record is created for emptying. Only items whose
`delete_checked` succeeded are passed to undo invalidation. **[read]**

Missing items are reported as skipped with the visible detail “already gone
from the Trash”; changed fingerprints or an unestablishable identity are
refused with “the item changed in the trash” or “Cannot verify this Trash item
is unchanged”. A mixed result continues with the rest of the confirmed list.
**[read]**

## Results, refresh and details

Empty Trash summaries now use the existing count model and report only what
happened. Examples covered by tests:

- `Emptied Trash: 3 items permanently deleted`
- `Deleted 2 of 3: 1 failed`
- `Deleted 1 of 4: 1 refused, 1 already gone, 1 cancelled`

The last form is not “Trash emptied”, so a mixed result with remaining entries
cannot claim success. The Trash page stores the job's failure/refusal/skip
details and exposes a **Details** button next to the status. Details show item
names and readable reasons, not internal URIs. After a job the page refreshes,
keeps only identities that still agree with the fresh listing, retains remaining
entries and drops stale selection. It does not dismiss the Trash page or touch
the hidden folder/split selection. **[read/observed]**

The existing UI-only `trash.empty`, dry-run, confirmation-required execution,
default Cancel, scoped job replies, close-before-response idle guard and
reviewer's stale-confirmation-state fix are unchanged. **[read]**
