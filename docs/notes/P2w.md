# P2w: a system-wide .deb and a signed apt repository on GitHub Pages

## What this change does

- Adds `packaging/debian/`: a source/binary `control` template, a Debian
  `changelog` template, and a DEP-5 `copyright` whose crate list was generated
  offline from `cargo metadata --format-version 1 --offline`.
- Adds `scripts/build-deb.sh <version>`. It builds
  `dist/gimbal-files_<version>_amd64.deb` from `target/release`, never runs
  cargo, strips the binaries, and lets `dpkg-shlibdeps` / `dpkg-gencontrol`
  fill in `Depends` and `Installed-Size`. The same file also provides the apt
  index and signing helpers shared with `scripts/release.sh`.
- Extends `scripts/release.sh`: the tarball is followed by the `.deb` and an
  apt repo update in the `dist/pages` worktree of `gh-pages`; the one publish
  prompt covers `gh release create` plus the branch commit and push. The push
  is last. `--dry-run` builds an unsigned repo in a scratch copy.
- Adds `scripts/test-deb.sh`, which runs a real `dpkg-deb` check, a scratch
  two-version signed repo and a rootless scratch apt update.
- Rewrites the README's install order: apt first, tarball for other
  distributions, and the notice-only update wording.

No Rust source, crate, `install.sh` or tarball format changed. There is no
`phase2/RULES.md`; I read `phase1/RULES.md` and the repository's `CLAUDE.md`,
which `phase2/README.md` names as its replacement. **[read]**

## The .deb

### Layout and modes

`scripts/build-deb.sh` stages a private tree under `$TMPDIR`, then calls
`dpkg-deb --root-owner-group --threads-max=1 --build`. The package contains
only:

```
./usr/bin/gimbal-files                                       0755 root/root
./usr/bin/gimbal-files-cli                                   0755 root/root
./usr/share/applications/io.github.kcanady21.GimbalFiles.desktop  0644 root/root
./usr/share/icons/hicolor/scalable/apps/io.github.kcanady21.GimbalFiles.svg  0644 root/root
./usr/share/doc/gimbal-files/copyright                       0644 root/root
./usr/share/doc/gimbal-files/changelog.Debian.gz             0644 root/root
```

plus their directories (0755). The desktop entry is the packaging file
unchanged, so `Exec=gimbal-files %U` finds `/usr/bin/gimbal-files` on PATH.
`--root-owner-group` is documented in `dpkg-deb(1)`. **[read]**

### Control fields

The template is `packaging/debian/control`; `build-deb.sh` removes its SPDX
comment lines and substitutes `@MAINTAINER@` and `@HOMEPAGE@`.
`dpkg-gencontrol -c… -P… -v… -T… -O…` writes the final `DEBIAN/control`.
Field names were checked against `deb-control(5)`:

- `Package`, `Version`, `Architecture` — required/recommended fields.
- `Maintainer` — "fullname-email", recommended. The value is published in the
  package; Kyle's name and email are not private once he publishes.
- `Description` — short line plus indented long lines.
- `Section`, `Priority` — general fields; this package uses `utils` and
  `optional`.
- `Installed-Size` — approximate installed KiB. `dpkg-gencontrol` computes it
  from `-P` per `deb-substvars(5)`, which accumulates regular files and
  symlinks in 1 KiB units plus 1 KiB baselines for other objects.
- `Homepage` — read from the `[workspace.package]` `repository` in
  `Cargo.toml`.
- `Depends` — generated by `dpkg-shlibdeps` from both binaries. `-e` includes
  one executable; `-T` writes/reads the shlibs substvars; `-O` prints rather
  than writing `debian/substvars` (`dpkg-shlibdeps(1)`).
- `Recommends` — `baobab`. `deb-control(5)` describes `Recommends` as packages
  normally installed together.

The version is native (`<version>`, no Debian revision), as allowed by
`deb-version(7)`. `dpkg-deb --info` on the test build shows:

```
Package: gimbal-files
Version: 0.1.0
Architecture: amd64
Maintainer: Test Person <test@example.invalid>
Installed-Size: 5320
Depends: libadwaita-1-0 (>= 1.5~beta), libc6 (>= 2.39), libcairo2 (>= 1.2.4), libgcc-s1 (>= 4.2), libgdk-pixbuf-2.0-0 (>= 2.31.1), libglib2.0-0t64 (>= 2.62.0), libgraphene-1.0-0 (>= 1.5.4), libgtk-4-1 (>= 4.21.5), libpango-1.0-0 (>= 1.14.0), libwayland-client0 (>= 1.11.0)
Recommends: baobab
Section: utils
Priority: optional
Homepage: https://github.com/Kcanady21/gimbal-files
Description: file manager for Wayland with tabs and a split view
```

The exact library minimums come from this machine's installed symbol files,
so they name `libgtk-4-1 (>= 4.21.5)` and `libadwaita-1-0 (>= 1.5~beta)` here.

### Reproducibility

## The apt repository

### Layout

Under the `gh-pages` worktree, `dist/pages/apt/`:

```
apt/pool/main/g/gimbal-files/*.deb
apt/dists/stable/main/binary-amd64/Packages
apt/dists/stable/main/binary-amd64/Packages.gz
apt/dists/stable/Release
apt/dists/stable/InRelease
apt/dists/stable/Release.gpg
apt/gimbal-files-archive-keyring.gpg
```

`dpkg-scanpackages --multiversion pool/main/g/gimbal-files` writes `Packages`
from the apt root, so every `Filename:` is relative to that root.
`dpkg-scanpackages(1)` notes that apt ignores uncompressed `Packages` except
on `file://` sources, so `Packages.gz` is written as well. `--multiversion`
keeps both versions in the index; without it only the newest version would be
listed. **[read]**

`Release` is generated in the script from `sha256sum` output, not by
`apt-ftparchive` (which is absent). It contains `Origin`, `Label`, `Suite`,
`Codename`, `Architectures`, `Components`, a `Description`, `Date` and the
`SHA256:` list with sizes. `apt-ftparchive`, `reprepro` and `aptly` were not
needed, and nothing was installed or downloaded. It deliberately has **no
`Valid-Until`**. This is the accepted risk recorded in the brief: without it, a
gap between releases cannot make apt reject the repository as expired; with
it, a stale mirror could replay an old index. For a single-maintainer repo the
first risk is the one Kyle chose to avoid. **[read]**

`InRelease` is `gpg --clearsign`; `Release.gpg` is
`gpg --detach-sign --armor`. Both use `--local-user "$GIMBAL_APT_KEY"` and
`--digest-algo SHA256`, never the default key. If `GIMBAL_APT_KEY` is empty or
the secret key is not in the keyring, the helper refuses with a message
pointing at the one-time setup. **[read]**

The public key is exported binary (dearmored) with `gpg --export` and copied
to `apt/gimbal-files-archive-keyring.gpg`. `apt_sign` refuses an armored
keyring with a message that names the `gpg --export` command. The repository
keeps the three newest versions by Debian version order and deletes older debs
from the pool before re-indexing. **[read]**

## release.sh

Existing checks are unchanged: on `main`, clean tracked and untracked tree,
local `main` equals `origin/main` after fetching, and `v<version>` absent
locally and remotely. `--dry-run --sign-only` is still refused, and a
relative `--notes` still resolves against the caller's folder. **[read]**

New behavior:

- After the tarball, `build-deb.sh` builds the `.deb`.
- `--dry-run` makes an unsigned repo tree in a `mktemp -d
  /tmp/gimbal-pages-dry-run.*` directory, copying any existing
  `dist/pages/apt` into it first. It does not create or touch the `gh-pages`
  worktree and does not run gpg or minisign. It leaves the scratch tree and
  prints its path.
- `--sign-only` signs the tarball, `latest.toml` and the apt repo in the real
  worktree, then exits without committing or pushing.
- A real release prepares the `gh-pages` worktree (creating a local orphan
  branch and saying so when `origin/gh-pages` does not exist), updates and
  signs the repo, signs the tarball, then asks the one
  `Publish v<version>? [y/N]` question.
- On yes, `gh release create` runs with the tarball, `.deb`, `latest.toml` and
  both minisign files. Only after it succeeds does the script commit
  `apt: gimbal-files <version>` in the worktree and
  `git push --set-upstream origin gh-pages`. A failed GitHub release therefore
  never moves apt to a version that has no download. **[read]**
- Both keys are required for signing: minisign's secret key and
  `GIMBAL_APT_KEY`. Error messages name `docs/notes/P2w.md` or the
  `sudo apt install minisign` command.

`GIMBAL_APT_KEYRING` is an extra, test-only override for the public keyring
path; the default is the committed
`packaging/gimbal-files-archive-keyring.gpg`. It is not a replacement for
`GIMBAL_APT_KEY`.

## README

The Install order is now:

1. **Install with apt** — the keyring download, the deb822
   `/etc/apt/sources.list.d/gimbal-files.sources` with
   `URIs: https://kcanady21.github.io/gimbal-files/apt`, `Suites: stable`,
   `Components: main`, `Architectures: amd64` and
   `Signed-By: /etc/apt/keyrings/gimbal-files.gpg`, then
   `sudo apt update && sudo apt install gimbal-files`.
2. **Updates and removal** — `sudo apt upgrade` (or `gimbal` on GimbalOS);
   `sudo apt remove gimbal-files` plus removing the two setup files to stop
   updates.
3. **Other distributions** — the signed tarball section, with the note that a
   per-user `~/.local/bin` install usually takes precedence over `/usr/bin`
   on PATH, so don't use both.
4. Source install, niri rule, default file manager, settings locations.

The apt setup uses the deb822 names from `sources.list(5)`: `Types`, `URIs`,
`Suites`, `Components`, `Architectures`, `Signed-By`. `sources.list(5)` says
`Signed-By` takes absolute keyring paths and recommends `/etc/apt/keyrings`
for system-operator keyrings. **[read]**

The Updates section is now notice-only: a daily check tells the user a new
version exists, but apt or the tarball performs the update, and a development
build never checks. It still says this check is not in the 0.1.0 build yet.

## Kyle's one-time steps

1. **Make the dedicated archive key.** Do not reuse another key. Pick an
   identity string you are willing to publish, and one of:

   ```sh
   gpg --quick-generate-key "Gimbal Files Archive <your@email>" ed25519 sign 0
   ```

   or, for RSA:

   ```sh
   gpg --quick-generate-key "Gimbal Files Archive <your@email>" rsa4096 sign 0
   ```

   Find the fingerprint:

   ```sh
   gpg --list-secret-keys --with-colons "Gimbal Files Archive"
   ```

   Export the **public** key binary (dearmored) and commit only that:

   ```sh
   gpg --export --output packaging/gimbal-files-archive-keyring.gpg <FINGERPRINT>
   ```

   The secret key stays in your GnuPG home and never enters the repo.

2. **Make the GitHub repository public** (`Kcanady21/gimbal-files`). Pages
   needs that.

3. **Settings → Pages**: choose the `gh-pages` branch, root folder. The first
   real release creates the branch locally and pushes it last.

4. **Set the release environment** in your shell profile:

   ```sh
   export GIMBAL_APT_KEY="<the archive key fingerprint>"
   export DEBFULLNAME="Your Name"
   export DEBEMAIL="your@email"
   ```

   `DEBFULLNAME`/`DEBEMAIL` are published in the `.deb` as `Maintainer: Your
   Name <your@email>`. If you prefer not to publish a personal address, use an
   address you are happy to see in `apt show gimbal-files`.

### Fixed: the gh-pages worktree was reused as it was

`prepare_pages_worktree` reused an existing `dist/pages` without comparing it to
`origin/gh-pages` and without clearing what an earlier run left there. Two failures followed:

- **A stranded release.** If the gh-pages push failed after `gh release create`, a rerun was
  refused because the tag now existed. The script only printed git's error.
- **A stale deb published.** A `--sign-only` run (or an aborted release) leaves its deb and
  indexes in the worktree. If the version then changed, the next real release would publish
  that deb with no GitHub release behind it.

Now `release.sh` handles the worktree like this:

- **Fetch:** it fetches `origin/gh-pages` first.
- **Find or create the worktree.** It reuses the worktree, or adds one from the local branch,
  from `origin/gh-pages` with tracking, or as a new orphan. The orphan now uses `git worktree add
  --orphan -b gh-pages` (git 2.42+; this machine has 2.53) instead of the detach, `rm` and `find
  -delete` sequence.
- **Reset:** it resets the worktree to the branch tip (`reset --hard`, `clean -fdx`). Everything
  in it is generated.
- **Compare with origin.** It fast-forwards to `origin/gh-pages`. If local gh-pages has commits
  that origin lacks, such as an earlier failed push, it refuses and prints the `git -C dist/pages
  push` to run.
- **On a failed commit or push**, it says that the tag is on GitHub and gives the command that
  finishes the apt half.

Tested on the scratch clone:

| Case | Result |
|---|---|
| First `--sign-only` | Orphan created, repo signed, nothing committed, origin has no gh-pages |
| Publish with `gh` failing | Exit 1, nothing committed or pushed |
| Publish with `gh` succeeding | `apt: gimbal-files 0.1.0` committed and pushed, branch tracks origin |
| A leftover `gimbal-files_0.0.9` deb in the worktree | Removed before indexing; not published |
| An unpushed local gh-pages commit | Refused with the push command |
| Worktree and local branch deleted | Re-added from `origin/gh-pages`, with history |

`main` stayed clean throughout. **[observed]**
