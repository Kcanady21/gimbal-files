## What I built

- `crates/fm-core/src/command/`: added the UI-only
  `trash.delete-permanently` command. It is `Effect::Files`, `undo=false`,
  requires repeated validated `items=<trash-item-uri>` using the existing
  `TrashItems` kind, keeps the registry-added `dry-run`, and has no empty-list
  or all-items meaning. `caller_allowed` refuses Hotkey, CLI and Agent before a
  handler or dry run. `permanently_deletes` detects the new Trash verb;
  the catalogue test now allows exactly `trash.empty` and
  `trash.delete-permanently`.
- `crates/fm-core/src/fileops/`: added `Request::DeleteSelected` and
  `Action::DeleteSelected`, plus `plan_selected`, `SelectedConfirmation`,
  `execute_selected` and one shared checked-deletion loop with
  `execute_empty`. The selected plan only queries the typed selected URIs; it
  never calls `list`. Changed or unverifiable items are refused; missing items
  are skipped by `delete_checked`; only successful deletions invalidate
  affected undo state and no undo record is created.
- `crates/fm-ui/src/trash.rs`: the item menu now has **Restore** and
  **Delete Permanently**. A right-click inside the selection uses the whole
  selected set; a right-click on an unselected row selects only that row. The
  click-time snapshot contains full `TrashIdentity` values, including
  fingerprints. The destructive dialog uses the exact selected count/name,
  default Cancel, close/escape Cancel and the destructive Delete Permanently
  response.
- `crates/fm-ui/src/app.rs`: the typed snapshot is staged in `Process` before
  the registry dispatch. It is taken once, deduplicated by validated URI, and
  its URI set must equal the command's `items` set before the worker is
  queued. A later selection change or monitor refresh cannot alter it.
- `crates/fm-ui/src/fileops/`: added the separate selected confirmation
  approval, worker wait and execution path. `OpKind`, progress, summaries and
  details distinguish selected permanent deletion from Empty Trash.
- `docs/notes/P2k2-r4.md`: this file.

No dependency, manifest, lockfile, workspace-model/session, header/layout,
spike, runner or desktop-configuration file was changed. **[observed]**

## Command and caller policy

The exact catalogue entry is:

```text
trash.delete-permanently items (trash item URIs) dry-run? (bool; default false)
```

The `items` argument is `Presence::Required`, so an invocation without items is
`MissingArgument`. Empty values and the root/foreign/traversal/non-canonical
URIs are refused by the existing `TrashUri` parser. There is no
`all`/`root`/`confirm` bypass argument and no default shortcut. **[read]**

`UI_ONLY_PERMANENT_COMMANDS` contains exactly `trash.empty` and
`trash.delete-permanently`. `permanently_deletes` also still detects unrelated
names such as `file.delete`, `file.remove` and `trash.delete`, so the catalogue
test would reject them; `file.trash` remains ordinary undoable trashing.
**[observed]**

## Selected snapshot and planning

`TrashBrowser::right_click` computes `menu_positions` from the current
selection and the clicked row, then `delete_snapshot` reads the full
`TrashItem` identities once. `TrashBrowser::delete_selected` stages that typed
vector in `Process` and dispatches `Invocation::new("trash.delete-permanently",
items...)` through the registry. `Process::take_trash_delete_for` removes the
snapshot once, deduplicates by URI and requires exact set equality with the
validated registry URIs. The worker receives `Request::DeleteSelected` with the
typed identities, never bare URIs. **[read/observed]**

`plan_selected` does not scan `trash:///`. It queries each selected URI once to
build the plan, and `delete_checked` re-queries immediately before GIO deletion.
An already-gone item becomes `Skipped`; a changed or unverifiable fingerprint is
refused with the existing readable reasons. A missing or stale item can never
turn into an empty-everything fallback. **[read/inferred]**

## Confirmation scope

The existing main-context path (`Process::fileop_empty_confirmation` →
`WindowUi::confirm_empty_trash` → `TrashBrowser::confirm_empty`) now branches on
the plan's request kind. Empty Trash and selected deletion share the dialog
lifecycle but not the authorisation:

- Empty Trash: title “Empty Trash?”, response id `empty`, Empty Trash button.
- Selected deletion: title “Permanently delete this item?” or
  “Permanently delete N items?”, body
  “These items will be permanently deleted. This cannot be undone.”, response id
  `delete`, Delete Permanently button, default/close/escape Cancel.
- The pending state is `(job id, ConfirmationKind)`. The worker waits for
  `ConfirmEmpty` or `ConfirmSelected` only on the matching request kind. Core
  uses distinct `EmptyConfirmation` and `SelectedConfirmation` types and binds
  the selected fingerprint to the operation name plus every identity. A
  different selected set is `ConfirmationMismatch`; ordinary `execute` returns
  `ConfirmationRequired`.
- The P2k closed-before-response idle guard and the r2 scoped stale-reply fix
  are retained. Leaving the page or closing its window cancels only the pending
  job. **[read/observed]**

## Checked deletion, results and undo

`execute_selected` and `execute_empty` share `execute_permanent`, which calls
`TrashBackend::delete_checked` for each valid top-level URI. The production
`GioTrash::delete_checked` still performs the immediate `revalidate_object`
query and then `gio::File::delete` on the exact requested `trash:///` URI. The
P2k2-r3 fixes are preserved: the requested URI is kept during metadata
conversion, external-drive escaped names and non-UTF-8 identities survive,
`NOFOLLOW_SYMLINKS` is used, an absent attribute is never a zero, and no
original-location path is used for deletion. **[read]**

GVfs removes a selected folder and its contents. The app does not recurse, run
`rm`, mount devices, delete the Trash root or sweep orphans. The accepted
practical query/delete race remains: another process can still change an object
between the query and GIO's delete. No atomic compare-and-delete or recursively
frozen tree is claimed. **[read/inferred]**

Summaries now include:

- `Permanently deleted 3 items`
- `Permanently deleted 2 of 3: 1 refused`
- `Permanently deleted 1 of 4: 1 refused, 1 already gone, 1 cancelled`
- `Permanent deletion cancelled`

A mixed result never says “Trash emptied”. Skipped selected items get the
visible detail “already gone from the Trash”. Progress, Cancel and Details use
the existing worker/row/dialog path. Cancellation of the final item remains
`Cancelled`, not `Failed`. No undo record is created; only identities whose
checked deletion succeeded are passed to undo invalidation. **[read/observed]**
