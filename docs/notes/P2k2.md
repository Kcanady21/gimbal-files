## Trash identity and validation

`TrashUri` is the identity. It accepts only `trash:///` followed by exactly one
canonical item name, never the root. It rejects a foreign scheme, uppercase
scheme, extra path segments, `.`/`..`, an encoded or raw `/`, NUL, malformed or
lowercase escapes, an escape of a byte GIO leaves raw, and any raw byte outside
GIO's path set. The decoded bytes are kept, so `%FF` round-trips as a non-UTF-8
`OsString`; the display name is never used as a key. `TrashIdentity` adds the
original path and deletion date, and `matches` treats a missing snapshot date or
original as unknown rather than as a change. **[observed]**

The production listing is the single `trash:///` namespace through GIO, so GVfs
selects the per-volume backend. Nothing falls back to
`~/.local/share/Trash`. A missing backend is `TrashError::Unavailable`. The
listed metadata is only `standard::name`, `standard::display-name`,
`standard::type`, `standard::icon`, `trash::orig-path` (byte string, never a
lossy string) and `trash::deletion-date`. A relative/absent original path is
`None`; a missing date is `None`. Both read as “Unknown” in the browser; the
former disables Restore for that item, the latter does not. **[observed]**

For the old P2f undo, `resolve_original` joins a relative top-directory path to
the mount top, including the `$topdir/.Trash/$uid` two-level form. The parser
tests cover both top-directory shapes and the home trash unchanged. **[observed]**

## Restore

`Request::Restore` carries the URI identities from the browser, and `request_for`
maps `trash.restore`. `FileOperations::plan` lists the backend once more and
re-reads each item's original path and date. It deduplicates by URI and builds a
`Step` with `action = Restore`, `trash = Some(identity)` and no local source
path. A missing item, a changed identity, an unknown original, a missing parent,
a non-writable parent and an existing target are separate conflicts. The missing
parent text is exactly “Original folder no longer exists”. **[observed]**

Execution uses the normal `Decisions` flow: the decision key is the original
target path, so Skip, Keep Both, Replace, Cancel and apply-to-all are the P2k
flow. Keep Both uses the existing `copy_name`/`free_copy_name` rule, per target
folder. Replace first trashes the existing target through GIO, never permanently
deletes it. Before writing, the executor revalidates the identity and checks the
original parent again. The restore itself is `gio::File::move_` with
`NOFOLLOW_SYMLINKS | NO_FALLBACK_FOR_MOVE`; a failure leaves the trash source in
place and is reported per item. Progress, Cancel and failure details use P2k.
Success is “Restored 3 items”; a partial run is “Restored 2 of 3: 1 failed”.
**[observed]**

A successful restore pushes `RecordKind::Restore` with the actual destination
path and its `(dev, ino)`. Undo checks that the same object is still at that
path; a replacement with the same name is `Conflict::Changed` and is refused.
The undo then re-trashes the restored items through GIO and restores any Replace
victim using the established `.trashinfo` safety checks and the freed-path set.
The integration child checks a Keep Both destination, and a Replace victim comes
back with the old contents. **[observed]**

## Empty Trash

A click dispatches `trash.empty`; the worker lists/building the plan off the
main thread. `Plan` for this request contains an immutable `Vec` of validated
identities. The worker sends that plan to the UI, which presents
`adw::AlertDialog`: “Empty Trash?”, the count, “These items will be permanently
deleted. This cannot be undone.”, Cancel (default/close/escape) and Empty Trash
(destructive). Only the destructive response sends `ConfirmEmpty`; a close or
Cancel sends the worker's cancel path. The P2k closed-before-response idle check
is used. `execute` itself refuses an `EmptyTrash` plan with
`ExecuteError::ConfirmationRequired`; only `execute_empty` accepts an
`EmptyConfirmation` bound to that exact plan. **[observed]**

The executor revalidates each identity against the current backend before
deleting. A changed or missing identity is refused, and the rest of the snapshot
continues. It never enumerates “everything present now”: items added after the
snapshot are absent from the plan and survive (tested). A successful delete goes
through the backend's top-level `g_file_delete`, as Nautilus does; the app never
deletes the root, a mount root, a metadata original path, or a local path
constructed from a URI. Cancel stops before the next item; deleted items are
reported, remaining entries stay visible. No undo record or Undo offer is
created. Status is “Emptied Trash: 3 items permanently deleted” or “Deleted 2 of
3: 1 failed”. `dry-run=true` lists the snapshot and writes nothing. **[observed]**

After a successful empty, older undo records that point at a deleted entry (or
whose recorded `files/name` no longer exists) are dropped, so a later item with
the same name cannot be mistaken for the old one. **[observed]**

## Trash browser

`trash.open` calls `WindowUi::open_trash`. The window owns at most one
`Rc<TrashBrowser>`; a second open presents the existing `adw::Dialog`, and a
close only clears that handle. The model's folder/split view is untouched, and
no tab is created. **[observed]**

The browser uses `ListView` + `MultiSelection` (virtualised) and lists in a
named short-lived thread, polling a channel from a 50 ms main-context timeout.
It shows “Loading Trash…”, “Trash is empty”, or the backend error. Each row
shows the GIO icon/fallback, display name, original location and local deletion
date/time; missing metadata says “Unknown”. Refresh keeps only selected URIs
that still exist in the new listing. A `GFileMonitor` on `trash:///` schedules a
150 ms refresh. Restore dispatches `trash.restore` with explicit URI arguments
for the restorable selected rows; the row menu exposes Restore. Empty Trash is
disabled with no items, an unavailable backend, a running job or an open
confirmation. Restore is disabled with no restorable selection. The in-dialog
progress row uses the P2k `ProgressView` and the job's Cancel. **[observed]**

The shared CSS adds only token-scaled trash classes (action row, row, icon,
name, metadata, empty label, status and progress); no fixed colours or sizes are
in the widget code. The existing header Trash button's drop target was left
unchanged. **[observed]**

**[read/observed] P1 blocker: URI reuse can empty an unconfirmed replacement.**
`trash.rs:254-272` treats missing original/date as no evidence of change. The
production identity contains only URI, original path and second-resolution date;
there is no object/revision token in LIST_ATTRIBUTES. Thus an entry removed after
confirmation and replaced at the same URI can match the old snapshot, certainly
when metadata is missing and also when original/date happen to be identical.
`execute_empty` revalidates through this matcher and permanently deletes the
replacement. A known date disappearing also passes. This violates the explicit
snapshot requirement that new/changed entries survive. Use a verified backend
object/revision identity and refuse permanent deletion when sameness cannot be
established. Do not “fix” it by requiring optional display metadata for Restore;
a missing date is allowed for restore, but is not proof of object identity.

**[read/observed] P2 blocker: restore conflicts are keyed by destination, not item.**
`mod.rs:345-353` returns original target as a restore decision key, and
`Decisions::new` deduplicates paths (`:462-478`). Two distinct deleted versions
of the same original path therefore share one answer. With an existing destination,
answering Skip for the first with apply-to-all off also answers the second; the UI
never offers independent choices. Replace can likewise spread unintentionally.
Key decisions by a unique step/item identity, while keeping the destination as the
human-readable conflict label. Preserve existing copy/move behavior.
